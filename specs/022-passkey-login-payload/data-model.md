# Data Model: Passkey Login Request Contract

## Entity: PasskeyAssertionPayload

- **Purpose**: Represents the assertion data returned by the authenticator after the user approves passkey sign-in.
- **Fields**:
  - `credentialId`: identifier for the selected passkey credential
  - `clientDataJSON`: client-produced assertion context returned from the browser
  - `authenticatorData`: authenticator-produced verification data
  - `signature`: proof generated by the authenticator for this login attempt
  - `userHandle`: optional account handle returned with the assertion when available
- **Validation rules**:
  - All required assertion fields must be present before the client sends the request
  - Optional fields must be clearly identified as optional
  - Assertion fields must remain separate from client-created login context

## Entity: LoginAttemptContext

- **Purpose**: Captures the non-assertion information needed to correlate the passkey login request to an account and challenge.
- **Fields**:
  - `accountIdentifier`: username, email, or account hint when the flow already knows it
  - `challengeReference`: correlation data tying the assertion to the server-issued challenge
- **Validation rules**:
  - The contract must define which context fields are required versus optional
  - Context must not duplicate assertion fields
  - Context must be sufficient for server correlation without adding unrelated device data

## Entity: PasskeyLoginResult

- **Purpose**: Represents the server response the client state layer receives after submitting a passkey login request.
- **Fields**:
  - `status`: success, invalid assertion, expired context, malformed request, or equivalent client-visible category
  - `userState`: signed-in user data when login succeeds
  - `message`: human-readable or client-displayable response summary
  - `retryGuidance`: whether the client should retry, re-request a challenge, or stop
- **Validation rules**:
  - Success responses must include enough information to update the client user state
  - Failure responses must distinguish unusable request data from failed credential verification
  - Response categories must be actionable by `State.login`

## State Transitions

1. **Challenge Ready**: The client has enough server-provided context to request a passkey assertion.
2. **Assertion Collected**: The browser returns passkey assertion data after user approval.
3. **Login Request Sent**: The client sends assertion data plus minimal login-attempt context to the server.
4. **Login Result Applied**: The client updates user state, retry state, or error state based on the server response category.
